### Гипотеза в рамках которой будем решать задачу

R&D-задачи, Тиражируемые подходы и вклад в обучение

### Описание задачи

- `О чем:` превратить `Figma Code Connect + MCP` из набора локальных успешных практик в общий надёжный слой между макетом, кодом и AI-агентом.
- `Проблема:` базовая польза уже подтверждена в нескольких местах, но процесс пока фрагментирован: покрытие неполное, внешние и вложенные компоненты не везде доведены, а устойчивой проверки рассинхрона `Figma ↔ code` нет.
- `Что просим:` довести покрытие, собрать reusable workflow для AI-агентов и сделать пилот с проверкой `Figma ↔ code` sync-check на `2-3` командах.

В качестве основного полигона проверки имеет смысл брать `gravity-ui/uikit`\.

Почему именно его:

- это базовая библиотека `React`-компонентов и токенов для `Gravity UI`, а не узкий продуктовый набор;
- она уже оформлена как самостоятельный `UIKit`-слой на `gravity-ui.com` и в репозитории `gravity-ui/uikit`;
- если гипотеза подтверждается на таком уровне, дальше её проще переносить на продуктовые библиотеки и конкретные дизайн-системы, собранные поверх `Gravity UI`\.

Внутри уже нашлись не только общие разговоры про `Figma Code Connect`, но и реальные внедрения:

- есть внутренние страницы и инструкции в `360`, `Realty Frontend` и других командах;
- в `HRDS` уже есть интеграция, где после подключения `Code Connect` в макете стал генерироваться код компонента с основными дизайн-стилями, а не только токены;
- в `Depot` уже сформулирован отдельный эксперимент: сначала прогнать вёрстку через `Figma MCP` без `Code Connect`, затем подключить `Code Connect` и сравнить результат;
- в `Arcadia` уже есть рабочие паттерны: `figma.config.json`, соседние `*.figma.ts(x)` файлы у компонентов, генерация `Icon.figma.tsx`, локальные publish/sync-скрипты.

Это значит, что задача уже не в том, чтобы доказать, что `Code Connect` в принципе полезен. Это уже видно. Задача в другом:

- собрать из локальных успехов общий стандарт;
- добить те части, которые мешают AI-агенту стабильно использовать этот слой;
- сделать так, чтобы польза не зависела от одной подготовленной команды или отдельного энтузиаста.

Ключевые ограничения текущего состояния:

- знания и практика распределены по отдельным командам, тикетам и README;
- покрытие завязано на конкретные дизайн-системы и отдельные компоненты, а не на общий стандарт;
- внешние и вложенные компоненты, а также сложные маппинги по пропсам доведены не везде;
- нет общего устойчивого процесса проверки рассинхрона `Figma ↔ code`, хотя локальные зачатки `sync-check` уже появляются;
- инструмент уже пробовали и внедряли точечно, но это ещё не массовый и дешёвый workflow.

Для пилота выбран консервативный технический подход:

- source of truth — deterministic `registry.json -> generated/*.figma.ts` workflow;
- publish/parse/preview — через официальный `@figma/code-connect` CLI;
- snippets — через официальный Template API `figma.helpers.react.renderProp` и `renderChildren`;
- проверка рассинхрона — отдельный `sync-check` по live Figma component metadata и локальному registry;
- внешние генераторы, `Code Connect UI` как основной источник связей и custom parser не входят в ближайший PR.

Такой выбор нужен не ради самих generated files, а ради воспроизводимого процесса:
одинаковый registry можно проверить локально, пересобрать, сравнить с Figma, preview-нуть snippets,
опубликовать через CLI и затем дать MCP/AI-агенту ссылку на реальные React-компоненты, imports и props.
`figma connect preview` при этом остаётся дополнительной проверкой published snippets, а не
обязательным pre-publish gate.

Если собрать из уже существующих локальных внедрений `Figma Code Connect + MCP` в устойчивый общий процесс, который:

- покрывает внешние компоненты;
- автоматически выявляет расхождения между компонентами и пропсами в `Figma` и в коде;
- даёт AI-агенту достоверную информацию о структуре макета и привязке к реальным компонентам;
- стандартизирует настройку и использование этого слоя хотя бы для нескольких пилотных команд,

то разработчики будут тратить на реализацию UI по макету на `20-30%` меньше времени, AI-ассистенты будут реже ошибаться при генерации UI-кода, а польза перестанет зависеть от отдельных энтузиастов и локального знания команды.

### Оценка задачи до AI эксперимента

Основной объём работы здесь не в том, чтобы изобрести новую технологию design-to-code, а в упаковке уже найденных локальных практик в reusable workflow:

- определить минимальный стандарт подключения нового компонента;
- добить покрытие внешних и проблемных компонентов;
- собрать понятный `publish/sync-check` контур;
- оформить `rules` / `skills` / workflow для AI-агентов;
- проверить, что эффект воспроизводится не на одной команде, а хотя бы на `2-3`\.

Baseline сейчас такой:

- внутри уже есть несколько локальных внедрений и экспериментов: `360`, `Realty Frontend`, `HRDS`, `Depot`, отдельные README и инструменты в `Arcadia`;
- есть подтверждённая польза на уровне отдельных компонентов и сценариев handoff;
- в качестве репрезентативной библиотеки для пилота можно использовать `gravity-ui/uikit` как базовый компонентный слой `Gravity UI`;
- часть времени на реализацию макета по-прежнему уходит на ручное восстановление соответствия между дизайном и кодом;
- нет одного стандартного способа подключить, поддерживать и проверять этот слой между `Figma`, кодом и AI;
- локальные решения есть, но они пока не сложились в общий дешёвый operational pattern для отдела.

### Бизнес-эффект

- Сокращается путь от макета до первого рабочего UI/PR.
- AI-агенты реже галлюцинируют компоненты, импорты и пропсы.
- Команды меньше зависят от экспертов, которые знают дизайн-систему и handoff-нюансы наизусть.
- Появляется переиспользуемый стандарт для `Figma ↔ code ↔ AI`, который можно раскатывать на другие продуктовые фронтенды.
- Дополнительно становится виднее, где сама дизайн-система рассинхронизирована между Figma и кодом.

### Метрики

- время от получения макета до первого рабочего UI/PR;
- время на доведение AI-сгенерированной вёрстки до merge-ready состояния;
- количество ошибок и фиксов из-за неверных компонентов, импортов и пропсов;
- доля задач, где реально используется `Code Connect + MCP`;
- доля задач, где используется автоматическая проверка `Figma ↔ code`;
- покрытие внешних компонентов;
- воспроизводимость эффекта хотя бы на `2-3` командах, а не только в одном уже подготовленном контуре.

### Сколько потребуется повышенных лицензий (Claude Code, Cursor) + Eliza

- `Подписки:` `2-3` мощные подписки для frontend/dev owners пилота
- `Eliza:` опционально, если нужно гонять benchmark или сравнивать модели

### Ожидаемые артефакты после эксперимента

- процесс, `CLI` или сервис проверки рассинхрона `Figma ↔ code`;
- покрытие внешних компонентов для `Code Connect`;
- пилотный контур и измеренный кейс на `gravity-ui/uikit`;
- минимальный стандарт подключения новых компонентов: `figma.config.json`, шаблон `*.figma.ts(x)` или `*.figma.js`, `publish/sync` workflow;
- инструкция для разработчиков и дизайнеров;
- `rules` / `skills` / workflow для AI-агентов, работающих с Figma через `MCP`;
- список того, что уже умеет базовый `Code Connect`, а что нужно добивать на нашей стороне;
- пилотные кейсы с измеренным эффектом;
- reusable operational pattern для других команд: как маппить компоненты, как публиковать связи, как проверять рассинхрон и как давать этот контекст AI-агентам в IDE и MCP-клиентах.
